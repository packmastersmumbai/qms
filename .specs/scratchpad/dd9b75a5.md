### Problem Definition (step by step)

Let's think step by step about what the user actually needs...

Step 1 — surface request: A visual warehouse floorplan map plus a real per-pallet location scheme, wired to the existing stock backend.

Step 2 — actual goal: Four operational capabilities. (1) Anyone can find where a material/lot physically is. (2) A manager can see inventory state visually (heatmap of full/empty). (3) A worker can record a movement even when the scanner is unavailable (tile-pick fallback). (4) Instant warehouse-wide stock view (KPI: % full, low-stock alerts).

Step 3 — business value: The backend already records stock and movements but there is no spatial/visual layer, so locations today are 8 logical zones, not physical slots. Users cannot answer "is the warehouse full?", "where is lot X?", or "which pallet position is free?" without walking the floor. The map turns invisible ledger data into a glanceable operational picture, reducing search time and mis-placement.

Step 4 — who benefits: Warehouse operators (find/place stock, record moves), supervisors/managers (occupancy + low-stock at a glance), QMS as a whole (accurate location data feeding trace).

Step 5 — future features: Phase 2 slot suggestion (min-tap putaway), optional posX/Y for sharper placement, geometry-driven pallet-count math. All explicitly deferred.

Step 6 — constraints: GAS double-iframe blocks CDN scripts → SVG+CSS only, no external JS libs. Native BarcodeDetector for QR. Blueprint aesthetic matching PM ISO print house-style. Must reuse existing backend functions verbatim — no new movement backend. Location ID regex `^[ABC]\d{3}$`. Light + dark themes. Bay = display/grouping only, never parsed from ID nor used in capacity math. Floorplan pixel-read counts (C/D = 42 each) must be verified on the floor before go-live.

Therefore, the root problem is: "The QMS records stock and movements in a ledger but has no spatial representation, so the warehouse's physical occupancy, the location of any given lot, and free pallet positions are all invisible — forcing staff to walk the floor and risking mis-placed inventory." The floorplan map + real per-pallet location scheme is the visual layer that makes existing backend data spatially actionable.

### Scope
- Included (Phase 1): reseed LOCATIONS → 148 pallet positions B001–B148 across bays A–F with Floor/Type/Bay columns; one new WarehouseFloorplan.html (to-scale/auto-grid map, 1-pallet occupancy heatmap, tap-position → contents, lot search highlight, KPI strip, tile-pick movement fallback calling existing backend).
- Included (Phase 2, later): MASTERS_Materials cols F→L geometry at material creation; saveMaterial regression fix (pad 5→12 cols); fit engine min(volume,weight) + suggestSlot(material, qty) with consolidation preference.
- Excluded: MASTERS_Floorplan self-referential tree, LEGO/drag-drop authoring builder, IQC form redesign, per-material location capacity, posX/Y coords (unless auto-grid wrong), any new movement backend, geometry seeding from category.
- Boundaries: no new stock/movement/scan backend written; Phase 1 capacity model is strictly 1 pallet per slot.

### Ambiguous Areas
- Exact pixel-read counts for bays C/D (42 each) — flagged in task as "verify on floor". Handled as a pre-go-live verification criterion, not a blocker.
- Whether posX/Y placement is needed — deferred; auto-grid fallback is the default.
- Two-phase split: parent already decided. Both phases stay in one task file; acceptance criteria are grouped per phase.

Step 3 — data entities: LOCATIONS sheet (Location ID `^[ABC]\d{3}$`, Floor col B, Type col I, Bay grouping col, capacity 1 pallet); STOCK_LEDGER (existing, scalar qty + running balance); lot/position mapping (whereIsLot); MASTERS_Materials (existing 5 cols; P2 adds F baseUnit, G eachL, H eachW, I eachH, J eachWeight, K perPallet, L fitClass).

Step 4 — constraints: SVG+CSS only (no CDN JS); native BarcodeDetector QR; blueprint aesthetic; light+dark; reuse getStockView/getStockSummary/getLowStockItems/whereIsLot/recordScan/recordLocationTransfer/issueRMForProduction verbatim; ID regex; Bay not in capacity math; 1 pallet/slot in P1.

Step 5 — implicit assumptions: existing backend functions work and return usable shapes; the 04 floorplan.jpg represents the 1st floor (letter B); QR is location-based (short, no symbols); occupancy = occupied slots ÷ total slots; a slot is occupied if any stock is assigned to it.

Therefore, key concepts: a spatial visual layer (map + heatmap + KPI) over an existing stock/movement/scan backend, backed by a reseeded flat LOCATIONS sheet of 148 physical 1-pallet positions, with a tile-pick movement fallback and a deferred Phase-2 geometry/slot-suggestion engine.

## Phase 3: Requirements Analysis

Let's think step by step about each requirement systematically...

Testability notes:
- "Heatmap shows occupancy" → testable: seed N occupied of 148, assert map colors N positions occupied and (148−N) empty, and % full = N/148.
- "Tap position → contents" → given a position with known stock, tapping shows exactly that material/lot/qty from getStockView.
- "Search lot → highlight" → given a lot at a known position, searching its ID highlights exactly that position; unknown lot shows a not-found message.
- "Movement fallback" → tile-picking a position and confirming calls the existing backend and the ledger reflects the move (no new backend).
- "Reseed" → after seed, LOCATIONS has 148 rows, IDs B001–B148 contiguous, each matches `^[ABC]\d{3}$`, bay counts A25/B4/C42/D42/E21/F14, Floor=B, Type per bay.

### Functional Requirements (Phase 1)
- FR1: LOCATIONS reseeded to exactly 148 rows, IDs B001–B148, all matching `^[ABC]\d{3}$`, contiguous, unique.
- FR2: Bay distribution A=25(RM), B=4(PM), C=42(PM), D=42(PM), E=21(FG), F=14(FG); Floor stored in col B, Type in col I, Bay in a display/grouping column; Bay never parsed from ID nor used in capacity.
- FR3: WarehouseFloorplan.html renders a map of all 148 positions grouped by bay, blueprint aesthetic, SVG+CSS only, no CDN scripts, working in light and dark.
- FR4: Occupancy heatmap — each position shown occupied or empty using 1-pallet-per-slot model; warehouse % full = occupied ÷ 148.
- FR5: Tapping a position shows what is stored there from getStockView (material/lot/qty), or an empty-state if nothing stored.
- FR6: Searching a lot highlights its position via whereIsLot; unknown lot shows a clear not-found message.
- FR7: KPI strip shows warehouse % full (getStockSummary) and low-stock alerts (getLowStockItems).
- FR8: Movement fallback — when scan is unavailable, user tile-picks a position and the move is recorded through existing recordScan/recordLocationTransfer/issueRMForProduction; no new movement backend is written.

### Functional Requirements (Phase 2 — later)
- FR9: MASTERS_Materials extended with cols F baseUnit, G eachL, H eachW, I eachH, J eachWeight, K perPallet, L fitClass, entered at material creation/edit; eachVolume computed not stored; fitClass is display hint only.
- FR10: Regression fix — saveMaterial writes all 12 columns (by column) so F→L are not truncated; existing 5-col rows still save correctly.
- FR11: Fit engine computes ceiling = min(volume, weight); suggestSlot(material, qty) walks open positions, keeps fitting ones, prefers a slot already holding the same material (consolidate), returns best; Accept records the movement.

### Non-Functional Requirements
- Compatibility: renders inside GAS double-iframe with no CDN/external scripts (SVG+CSS only); light and dark themes.
- Usability: map is glanceable — occupancy readable at a glance; movement fallback minimizes taps.
- Reliability: reuses existing backend verbatim; no new movement path introduced in P1.
- Aesthetic: architectural blueprint matching PM ISO print house-style.
- Data integrity: all location IDs satisfy `^[ABC]\d{3}$`; counts verified on floor before go-live.

### Constraints & Assumptions
- No CDN JS (double-iframe). Native BarcodeDetector for QR. Backend reused verbatim. Bay is display-only. 1 pallet/slot in P1. 04 floorplan.jpg = 1st floor (letter B). Pixel-read counts C/D=42 need floor verification.

### Measurable Outcomes
- 148 valid contiguous location rows exist.
- Map renders all 148 positions in both themes with correct bay grouping.
- Occupancy %, tap-to-contents, lot-search-highlight, KPI strip, and tile-pick fallback all function against the existing backend.

### User Scenarios

Primary (happy path):
1. Manager opens WarehouseFloorplan.html; map renders 148 positions grouped by bay with occupancy heatmap and KPI strip (% full, low-stock alerts).
2. Operator searches a lot ID; its position highlights.
3. Operator taps a position; contents (material/lot/qty) display.
4. Scanner unavailable → operator tile-picks a position and confirms; move recorded via existing backend.

Alternative:
- Empty warehouse → all positions shown empty, 0% full.
- Phase 2 → operator receives stock, suggestSlot proposes best slot, taps Accept, move recorded.

Error:
- Lot search no match → "Lot not found" message, no position highlighted.
- Tap empty position → empty-state ("No stock in this position").
- BarcodeDetector unsupported → tile-pick fallback available.
- Floor count mismatch during verification → seed corrected before go-live.
- Full warehouse, no free slot for tile-pick/suggest → "No available position" message.
